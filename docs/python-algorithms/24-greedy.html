그리디

그리디는 매 순간 가장 좋아 보이는 것을 고르고 뒤를 돌아보지 않는 방법입니다. 코드는 짧고 빠르지만, 그 선택이 끝까지 옳다는 근거가 있을 때만 정답이 됩니다.

탐욕 선택정렬 후 선택반례교환 논증vs DP

이 장에서 배울 것

  • 그리디가 무엇이고 완전 탐색·DP와 어떻게 다른지 설명할 수 있다
  • 그리디가 되는 조건을 교환 논증으로 확인할 수 있다
  • 작은 입력을 전부 돌려 반례를 찾는 방법을 안다
  • 정렬 후 고르기, 힙으로 가장 작은 둘 합치기 같은 대표 모양을 안다
  • 그리디가 안 되는 문제를 알아보고 DP로 넘기는 기준을 안다

그리디란

핵심

그리디는 매 순간 가장 좋아 보이는 것을 고르고 되돌아가지 않는 방법이다. 빠르지만, "지금의 최선이 전체의 최선"이라는 조건이 성립할 때만 맞는다.

그리디(greedy, 탐욕법)는 선택의 순간마다 한 가지 기준으로 가장 좋은 것을 집고, 그 선택을 다시 바꾸지 않는다. 갈림길마다 목적지에 가장 가까워 보이는 길로만 꺾는 것과 같다. 대부분 잘 가지만, 그 길이 막다른 길이면 돌아올 수 없다.

같은 문제를 푸는 다른 방법과 한 줄씩 비교하면 그리디의 자리가 보인다. 완전 탐색은 22장, DP(Dynamic Programming, 다이나믹 프로그래밍)는 26장에서 다룬다.

방법어떻게 푸는가속도정답 보장
완전 탐색가능한 선택을 모두 만들어 본다느리다. 지수 시간이 흔하다항상
DP작은 문제의 답을 저장해 두고 모든 선택을 비교한다중간. 상태 수에 비례한다항상
그리디한 가지 기준으로 한 길만 간다빠르다. 정렬 한 번이 대부분이다조건이 맞을 때만

그리디 풀이의 코드는 대개 "정렬하고 한 번 훑기"라 몇 줄이면 끝난다. 어려운 것은 코드가 아니라 이 기준으로 골라도 되는가를 확인하는 일이다. 이 장은 그 확인 방법을 다룬다. 14장의 다익스트라, 29장의 크루스칼처럼 뒤에서 만날 이름난 알고리즘도 그리디다.

되는 조건: 교환해도 나빠지지 않는다

그리디가 정답을 내려면 두 가지가 성립해야 한다. 이름은 딱딱하지만 뜻은 단순하다.

  • 탐욕 선택 속성 — 지금 가장 좋아 보이는 선택을 포함하는 최적해가 반드시 있다. 즉 이 선택을 해도 정답으로 가는 길이 막히지 않는다.
  • 최적 부분 구조 — 그 선택을 하고 남은 문제가 원래와 같은 모양의 더 작은 문제이고, 작은 문제의 최적해에 지금 선택을 더하면 전체의 최적해가 된다.

두 번째는 대개 자연스럽게 성립한다. 문제는 첫 번째다. 이것을 확인하는 가장 쓸모 있는 도구가 교환 논증이다. 생각의 틀은 이렇다. "정답이 내 선택과 다르다고 하자. 정답의 그 자리를 내 선택으로 바꿔 넣어도 나빠지지 않는다면, 내 선택을 포함하는 정답이 있다." 바꿔 넣어도 손해가 없으니 처음부터 내 선택을 해도 된다는 뜻이다.

숫자 카드를 한 줄로 늘어놓아 가장 큰 수를 만드는 문제로 확인해 보자. 직관대로 큰 숫자부터 놓으면 된다.


def largest_number(digits: list[int]) -> str:
    ordered = sorted(digits, reverse=True)      # 큰 숫자부터
    return ''.join(map(str, ordered))


print(largest_number([3, 9, 1, 9, 4]))

99431

교환 논증을 적용하면 이렇다. 어떤 배열에서 작은 숫자가 큰 숫자보다 앞에 있다면, 둘을 맞바꾸는 순간 수가 커진다. 그러므로 가장 큰 수에서는 큰 숫자가 작은 숫자보다 앞에 있을 수밖에 없다. 첫 자리는 가장 큰 숫자여야 하고(탐욕 선택 속성), 첫 자리를 정하고 나면 나머지 숫자로 가장 큰 수를 만드는 똑같은 문제가 남는다(최적 부분 구조).

이렇게 "내 기준과 어긋난 두 원소를 맞바꾸면 손해인가, 이득인가"를 따지는 것이 교환 논증의 전부다. 이 장의 예제마다 같은 질문을 던진다.

동전 거스름돈: 되는 경우와 안 되는 경우

거스름돈을 가장 적은 동전 수로 주는 문제는 그리디의 교과서 예제다. 큰 동전부터 가능한 만큼 쓰면 된다. 같은 코드에 동전 종류만 바꿔 두 번 돌려 보자.


def greedy_change(coins: list[int], amount: int) -> list[int]:
    used = []
    for coin in sorted(coins, reverse=True):     # 큰 동전부터
        count, amount = divmod(amount, coin)     # 이 동전을 최대한 쓴다
        used.extend([coin] * count)
    return used


print(greedy_change([10, 50, 100, 500], 1260))
print(greedy_change([1, 3, 4], 6))

[500, 500, 100, 100, 50, 10]
[4, 1, 1]

1260원은 동전 6개로 정확히 최소다. 그런데 1·3·4원짜리로 6원을 거슬러 주는 두 번째 결과는 틀렸다. 그리디는 4 + 1 + 1로 3개를 썼지만 3 + 3이면 2개다. 같은 코드가 한쪽에서는 맞고 다른 쪽에서는 틀린다. 차이는 코드가 아니라 입력의 성질에 있다.

500·100·50·10원은 각 동전이 바로 아래 동전의 배수다. 그래서 교환 논증이 통한다. 어떤 정답이 500원짜리를 쓸 수 있는데 안 썼다면, 그 자리를 채운 작은 동전들(100원 다섯 개든 50원 열 개든)은 정확히 500원짜리 하나로 바꿀 수 있고, 바꾸면 개수가 줄어든다. 즉 큰 동전을 안 쓰는 정답은 없다. 1·3·4원은 배수 관계가 아니라서 4원 하나가 3원짜리로 깔끔하게 바뀌지 않고, 그 틈에서 반례가 생긴다.

이런 반례를 머릿속으로 찾기는 어렵다. 대신 작은 입력을 전부 돌려 완전 탐색과 답을 비교하면 된다. 7장의 combinations_with_replacement로 동전 k개를 고르는 모든 경우를 만들어 진짜 최소 개수를 구하고, 그리디와 답이 다른 금액을 찾는다.


from itertools import combinations_with_replacement


def greedy_count(coins: list[int], amount: int) -> int:
    count = 0
    for coin in sorted(coins, reverse=True):
        used, amount = divmod(amount, coin)
        count += used
    return count


def exact_count(coins: list[int], amount: int) -> int:
    for k in range(1, amount + 1):               # 동전 1개부터 늘려 가며
        for combo in combinations_with_replacement(coins, k):
            if sum(combo) == amount:
                return k                         # 처음 만든 k 가 최소다
    return 0


coins = [1, 3, 4]
for amount in range(1, 11):
    greedy, exact = greedy_count(coins, amount), exact_count(coins, amount)
    if greedy != exact:
        print(f'{amount}원: 그리디 {greedy}개, 최소 {exact}개')

6원: 그리디 3개, 최소 2개
10원: 그리디 4개, 최소 3개

10원 이하에서 두 금액이 걸렸다. 반례가 하나라도 나오면 그 그리디는 버린다. 이 "작은 입력 전수 비교"는 그리디를 제출하기 전에 가장 싸게 할 수 있는 검증이다. 배수 관계가 아닌 동전 문제는 26장의 DP로 푼다.

정렬 후 고르기: 회의실 배정

그리디 문제의 가장 흔한 모양은 한 가지 기준으로 정렬한 뒤 앞에서부터 조건에 맞는 것만 고르는 것이다. 정렬이 O(n log n)이고 훑기가 O(n)이라 전체도 O(n log n)이다. 기준을 어떻게 잡느냐가 전부라서, 같은 문제에 기준 두 개를 적용해 비교해 보자.

회의실 하나에 회의 여섯 개가 신청됐다. 각 회의는 (시작, 끝) 시각으로 주어지고, 겹치지 않게 가장 많은 회의를 고르려 한다. 앞 회의가 끝나는 시각에 다음 회의가 시작해도 된다.

먼저 떠오르는 기준은 "일찍 시작하는 회의부터"다. 그러나 시작 시각 순으로 고르면 가장 먼저 시작하는 A(0, 5)를 집고, A가 끝날 때까지 B·C·D를 모두 버리게 된다. 길이가 짧은 회의부터 고르는 것도 틀린다. 짧은 회의 하나가 긴 회의 둘에 걸쳐 있으면 하나를 얻고 둘을 잃는다. 맞는 기준은 일찍 끝나는 회의부터다.


meetings = [(0, 5), (1, 3), (3, 4), (4, 6), (5, 7), (6, 8)]   # A~F


def pick_meetings(meetings: list[tuple[int, int]], key) -> list[tuple[int, int]]:
    chosen = []
    last_end = 0
    for start, end in sorted(meetings, key=key):
        if start >= last_end:            # 앞 회의가 끝난 뒤에 시작하면 고른다
            chosen.append((start, end))
            last_end = end
    return chosen


print(pick_meetings(meetings, key=lambda m: m[0]))   # 시작 시각 순
print(pick_meetings(meetings, key=lambda m: m[1]))   # 끝나는 시각 순

[(0, 5), (5, 7)]
[(1, 3), (3, 4), (4, 6), (6, 8)]

시작 시각 순은 2개, 끝나는 시각 순은 4개다. 왜 끝나는 시각인지는 교환 논증으로 설명된다. 가장 일찍 끝나는 회의를 B라 하자. 어떤 정답이 B를 안 골랐다면, 그 정답에서 가장 먼저 끝나는 회의 X를 B로 바꿔 넣어 보자. B는 X보다 늦게 끝나지 않으므로 X 뒤에 오던 회의들과 여전히 겹치지 않는다. 개수는 그대로다. 즉 가장 일찍 끝나는 회의를 포함하는 정답이 반드시 있다. 그것을 고르고 나면 "그 끝 시각 이후에 시작하는 회의들"로 같은 문제가 남는다.

일찍 끝나는 회의를 고를수록 뒤에 남는 시간이 가장 길다. 이 "남는 자원을 가장 많이 남기는 선택"이 정렬 후 고르기 문제에서 기준을 찾는 단서다. key에 넘기는 함수와 튜플 기준은 3장에서 다뤘다.

자주 나오는 모양

그리디 문제는 모양이 몇 가지로 정해져 있다. 기준을 찾을 때 먼저 이 셋에 끼워 맞춰 본다.

모양기준예도구
큰 것부터단위당 이득이 큰 순분수 배낭, 동전 거스름돈sorted(..., reverse=True)
작은 것부터비용이 작은 순, 일찍 끝나는 순대기 시간 최소화, 회의실 배정sorted(...)

큰 것부터: 분수 배낭

배낭에 담을 수 있는 무게가 정해져 있고, 물건마다 (무게, 가치)가 있다. 물건을 잘라서 일부만 담아도 된다면, 무게 1당 가치가 큰 물건부터 담고 마지막 물건만 남은 무게만큼 잘라 넣는다.


def fractional_knapsack(items: list[tuple[int, int]], capacity: int) -> float:
    by_density = sorted(items, key=lambda it: it[1] / it[0], reverse=True)
    total_value = 0.0
    for weight, value in by_density:            # 무게당 가치가 큰 순
        take = min(weight, capacity)             # 들어가는 만큼만
        total_value += value * take / weight
        capacity -= take
        if capacity == 0:
            break
    return total_value


print(fractional_knapsack([(6, 66), (5, 50), (5, 50)], 10))

106.0

무게당 가치가 11인 (6, 66)을 통째로 담고, 남은 4만큼 (5, 50)을 잘라 40을 얻는다. 교환 논증은 간단하다. 밀도가 낮은 물건이 조금이라도 들어 있다면 그만큼을 밀도 높은 물건으로 바꿔 넣는 편이 항상 이득이다. 자를 수 있어서 이 교환이 늘 가능하다. 자를 수 없게 되는 순간 어떻게 되는지는 다음 절에서 본다.

작은 것부터: 대기 시간 최소화

창구 하나에 사람 n명이 줄을 선다. 각자 일을 보는 데 걸리는 시간이 다를 때, 모든 사람이 자기 일을 마칠 때까지 기다린 시간의 합을 가장 작게 하려면 짧은 사람부터 세운다.


def total_waiting(service_times: list[int]) -> int:
    finished_at = 0
    total = 0
    for t in service_times:
        finished_at += t          # 이 사람이 일을 마치는 시각
        total += finished_at
    return total


times = [5, 1, 3, 2]
print(total_waiting(times))
print(total_waiting(sorted(times)))   # 짧은 사람부터

31
21

앞사람의 시간은 뒤에 선 모든 사람이 함께 기다린다. 그래서 줄에서 긴 사람이 짧은 사람 바로 앞에 있다면 둘을 맞바꾸자. 다른 사람들의 대기 시간은 그대로이고, 맞바꾼 두 사람 중 짧은 쪽이 먼저 끝나므로 합은 줄어든다. 어긋난 쌍이 하나도 없는 순서, 즉 오름차순이 최선이다.

힙으로 가장 작은 둘 합치기: 카드 합치기

숫자가 적힌 카드 묶음들을 하나로 합친다. 두 묶음을 합치는 비용은 두 묶음의 합이고, 합친 묶음은 다시 합칠 수 있다. 총비용을 최소로 하려면 매번 가장 작은 두 묶음을 합친다. 먼저 합친 묶음일수록 이후 합치기에 여러 번 끼어 비용에 거듭 더해지므로, 작은 것을 먼저 합쳐 여러 번 더해지게 하고 큰 것은 늦게 합쳐 적게 더해지게 하는 것이다.

한 번 합치면 "가장 작은 둘"이 바뀌므로 정렬 한 번으로는 안 된다. 넣고 빼면서 최솟값을 유지하는 7장의 heapq가 꼭 맞는다.


import heapq


def min_merge_cost(piles: list[int]) -> int:
    heap = list(piles)
    heapq.heapify(heap)
    cost = 0
    while len(heap) > 1:
        a = heapq.heappop(heap)           # 가장 작은 둘을 꺼내
        b = heapq.heappop(heap)
        merged = a + b
        cost += merged
        heapq.heappush(heap, merged)      # 합친 묶음을 다시 넣는다
        print(f'{a} + {b} = {merged}')
    return cost


print(min_merge_cost([10, 20, 40]))

10 + 20 = 30
30 + 40 = 70
100

40과 20을 먼저 합쳤다면 60, 그다음 70으로 총 130이다. 묶음이 n개면 합치기가 n-1번이고 힙 연산이 O(log n)이라 전체 O(n log n)이다.

그리디가 안 되면: 0/1 배낭

분수 배낭에서 조건 하나만 바꾼다. 물건을 자를 수 없고, 통째로 넣거나 빼야 한다. 이것이 0/1 배낭이다. 무게당 가치 순 그리디는 같은 물건으로도 바로 틀린다. 진짜 답은 7장의 combinations로 물건을 고르는 모든 경우를 만들어 구한다.


from itertools import combinations


def knapsack_greedy(items: list[tuple[int, int]], capacity: int) -> int:
    by_density = sorted(items, key=lambda it: it[1] / it[0], reverse=True)
    total_value = 0
    for weight, value in by_density:
        if weight <= capacity:              # 통째로 들어갈 때만
            capacity -= weight
            total_value += value
    return total_value


def knapsack_exact(items: list[tuple[int, int]], capacity: int) -> int:
    best = 0
    for k in range(len(items) + 1):          # 물건 k개를 고르는 모든 경우
        for chosen in combinations(items, k):
            weight = sum(w for w, v in chosen)
            value = sum(v for w, v in chosen)
            if weight <= capacity:
                best = max(best, value)
    return best


items = [(6, 66), (5, 50), (5, 50)]
print(knapsack_greedy(items, 10))
print(knapsack_exact(items, 10))

66
100

밀도가 가장 높은 (6, 66)을 넣는 순간 남은 무게 4에는 아무것도 못 넣는다. (5, 50) 둘을 넣으면 100이다. 교환 논증이 깨지는 지점을 보자. 분수 배낭에서는 밀도 낮은 물건 "일부"를 밀도 높은 물건 "일부"로 바꿀 수 있었다. 자를 수 없으면 (5, 50) 하나를 (6, 66)으로 바꾸는 순간 무게가 넘쳐 다른 물건까지 빼야 한다. 지금의 선택이 뒤의 선택지를 바꾸는데, 그 영향을 지금 알 수 없으면 그리디는 안 된다.

이럴 때는 선택을 하나로 정하지 않고 "넣는 경우"와 "안 넣는 경우"를 모두 따라가되, 같은 상태(남은 물건, 남은 무게)의 답은 저장해 다시 쓴다. 이것이 26장의 DP다. 26장에서 이 배낭을 dp[i][w] 표로 푼다.

그리디와 DP 사이에서 고르는 순서는 다음과 같다.

  1. 기준을 하나 세우고 작은 입력에서 완전 탐색과 답을 비교한다. 반례가 나오면 그리디가 아니다.
  2. 반례가 없으면 교환 논증을 써 본다. "정답의 한 자리를 내 선택으로 바꿔도 손해가 없다"가 말이 되면 그리디다.
  3. 교환이 다른 선택에 연쇄로 영향을 주면 DP를 떠올린다. 이때 상태 수가 1초에 처리할 수 있는 연산 수를 넘지 않는지 확인한다(2장).

반대도 중요하다. 그리디로 풀리는 문제를 DP로 풀면 상태 수만큼 시간이 든다. n이 10만이고 값이 10⁹이면 DP 표는 만들 수도 없지만, 정렬 한 번은 바로 끝난다. 그래서 둘 다 되는 문제라면 그리디가 먼저다.

자주 하는 실수

반례를 찾지 않고 제출하기

"그럴듯하다"는 근거가 아니다. 기준을 정했으면 원소 3~5개짜리 입력을 손으로 몇 개 만들어 보고, 시간이 있으면 find_counterexample.py처럼 작은 입력을 전부 돌려 완전 탐색과 비교한다. 예제 입력이 통과했다는 것은 반례가 없다는 뜻이 아니다.

정렬 기준을 잘못 잡기

회의실 배정을 시작 시각이나 길이 순으로 정렬하는 것이 대표적이다. 기준이 틀리면 코드가 아무리 맞아도 답이 틀린다. 후보 기준이 여럿이면 각각 반례를 찾아 보고, 교환 논증이 되는 기준만 남긴다.

동률을 그냥 두기

정렬 기준 값이 같은 원소의 순서가 답을 바꾸기도 한다. 회의실 배정에서 끝나는 시각이 같은 회의가 있고 그중에 길이가 0인 회의가 끼면, 끝나는 시각만으로 정렬했을 때 틀릴 수 있다.


meetings = [(2, 2), (1, 2), (2, 3)]


def count_meetings(meetings: list[tuple[int, int]], key) -> int:
    count = 0
    last_end = 0
    for start, end in sorted(meetings, key=key):
        if start >= last_end:
            count += 1
            last_end = end
    return count


print(count_meetings(meetings, key=lambda m: m[1]))           # 끝나는 시각만
print(count_meetings(meetings, key=lambda m: (m[1], m[0])))   # 끝, 같으면 시작

2
3

끝나는 시각만으로 정렬하면 (2, 2)와 (1, 2)의 순서가 입력 순서대로 남고(안정 정렬, 3장), (2, 2)를 먼저 고르는 바람에 (1, 2)를 버린다. 끝이 같으면 시작이 빠른 쪽을 먼저 보도록 (끝, 시작) 튜플로 정렬하면 셋 다 고른다. 동률이 생길 수 있는 문제라면 두 번째 기준까지 적는 습관을 들인다.

그리디가 되는데 DP로 풀어 시간 초과

배낭 문제 모양만 보고 DP 표를 만들면, 자를 수 있는 분수 배낭처럼 그리디가 되는 문제에서도 상태 수만큼 시간이 든다. 값의 범위가 10⁹처럼 크면 표를 만들 수조차 없다. 먼저 그리디 기준이 있는지 보고, 없을 때 DP로 간다.

회의실 배정

회의실이 하나 있고 회의 N개가 신청됐다. 각 회의는 시작 시각 s와 끝 시각 e(0 ≤ s ≤ e ≤ 10⁹)로 주어진다. 서로 겹치지 않게 회의를 골라 진행할 때, 최대 몇 개를 진행할 수 있는지 출력하라. 한 회의가 끝나는 시각에 다음 회의가 바로 시작해도 된다. 시작과 끝이 같은 회의도 있을 수 있다.

첫 줄에 N(1 ≤ N ≤ 100,000)이 주어지고, 다음 N줄에 각 회의의 s와 e가 공백으로 구분되어 주어진다.

접근 방법먼저 생각해 보고 펼치세요

가장 일찍 끝나는 회의를 고르는 것은 손해가 아니다. 그 회의 대신 다른 회의를 먼저 하는 정답이 있어도, 그 자리를 가장 일찍 끝나는 회의로 바꾸면 뒤의 회의들과 여전히 겹치지 않는다.

  1. 회의를 (끝, 시작) 순으로 정렬한다. 끝이 같으면 시작이 빠른 쪽이 앞이다.
  2. 마지막으로 고른 회의의 끝 시각 last_end를 0으로 두고 앞에서부터 훑는다.
  3. 시작 시각이 last_end 이상이면 고르고 last_end를 그 회의의 끝으로 바꾼다. 아니면 건너뛴다.
  4. 고른 개수를 출력한다.
풀이 코드 

import sys

input = sys.stdin.readline

n = int(input())
meetings = [tuple(map(int, input().split())) for _ in range(n)]
meetings.sort(key=lambda m: (m[1], m[0]))    # 끝나는 시각, 같으면 시작 시각

count = 0
last_end = 0
for start, end in meetings:
    if start >= last_end:                    # 앞 회의가 끝난 뒤 시작하면
        count += 1
        last_end = end
print(count)

스스로 확인

500·100·50·10원에서는 큰 동전부터 쓰는 그리디가 맞고, 1·3·4원에서는 틀리는 이유는?

앞의 동전들은 각각 바로 아래 동전의 배수라서, 큰 동전 하나 자리를 작은 동전들로 채운 정답은 언제나 큰 동전 하나로 바꿔 개수를 줄일 수 있다. 1·3·4원은 배수 관계가 아니라 이 교환이 안 되고, 6원(4+1+1 대 3+3)이 반례다.

회의실 배정에서 시작 시각 순으로 고르면 왜 틀리는가?

일찍 시작하지만 오래 걸리는 회의 하나가 그 사이의 짧은 회의 여럿을 모두 막기 때문이다. 일찍 끝나는 회의를 고르면 뒤에 남는 시간이 가장 길어 손해가 없다.

대기 시간 최소화에서 "짧은 사람부터"를 교환 논증으로 설명하면?

긴 사람이 짧은 사람 바로 앞에 있다면 둘을 맞바꾼다. 다른 사람들의 대기 시간은 그대로이고 두 사람 중 짧은 쪽이 먼저 끝나므로 합이 줄어든다. 어긋난 쌍이 없는 순서는 오름차순뿐이다.

분수 배낭은 무게당 가치 순 그리디가 되는데 0/1 배낭은 안 되는 이유는?

분수 배낭은 밀도 낮은 물건의 일부를 밀도 높은 물건의 일부로 언제나 바꿔 넣을 수 있다. 자를 수 없으면 바꿔 넣는 순간 무게가 넘쳐 다른 선택까지 바뀌므로 교환 논증이 깨진다. 0/1 배낭은 26장의 DP로 푼다.

정리

  1. 그리디는 매 순간 한 가지 기준으로 가장 좋은 것을 고르고 되돌아가지 않는다. 코드는 짧고 빠르지만 조건이 맞을 때만 정답이다.
  2. 되는 조건은 탐욕 선택 속성과 최적 부분 구조다. "정답의 한 자리를 내 선택으로 바꿔도 손해가 없다"는 교환 논증으로 확인한다.
  3. 그리디를 제출하기 전에 작은 입력을 전부 돌려 완전 탐색과 답을 비교한다. 반례가 하나라도 나오면 버린다.
  4. 가장 흔한 모양은 정렬 후 고르기다. 회의실 배정은 끝나는 시각 순이고, 동률은 두 번째 기준으로 정리한다.
  5. 큰 것부터(분수 배낭), 작은 것부터(대기 시간), 매번 가장 작은 둘 합치기(카드 합치기, heapq)가 대표 모양이다.
  6. 지금 선택이 뒤의 선택지를 바꾸고 그 영향을 지금 알 수 없으면 그리디가 아니다. 0/1 배낭처럼 선택이 얽히면 26장 DP로 간다.
