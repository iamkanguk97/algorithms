본문으로 건너뛰기

누적합

같은 배열에 구간을 묻는 질문이 수만 번 들어오면, 매번 다시 더하는 대신 한 번 미리 더해 두는 편이 훨씬 빠릅니다. 이 장에서는 구간 합을 빼기 한 번으로 구하는 누적합과, 그 거울인 차분 배열을 함께 다룹니다.

구간 합2차원 누적합차분 배열포함-배제O(1) 질의

이 장에서 배울 것

  • 질의를 점과 구간, get과 update로 나눠 어떤 도구가 맞는지 고를 수 있다
  • 길이 n+1의 누적합 배열을 만들고 구간 합을 O(1)에 구할 수 있다
  • 합 말고 어떤 연산이 누적합으로 되고 어떤 연산이 안 되는지 안다
  • 2차원 누적합을 포함-배제로 만들고 직사각형의 합을 구할 수 있다
  • 차분 배열로 구간 더하기를 모아 처리하고, 누적합과의 대칭을 설명할 수 있다

점과 구간, get과 update

핵심

누적합은 구간 get을 점 get 두 번으로, 차분 배열은 구간 update를 점 update 두 번으로 바꾸는 기술이다.

이 장은 네 단어로 설명된다. get은 값을 읽기만 하는 질의이고, update는 값을 고치는 질의다. 점은 칸 하나, 구간은 이어진 여러 칸이다. 보통 리스트에서 점 작업은 빠르고 구간 작업은 느리다.


a = [4, 7, 2, 9, 5]

print(a[2])              # 점 get: 칸 하나 읽기
print(sum(a[1:4]))       # 구간 get: 1~3번 칸을 모두 더한다

a[2] += 10               # 점 update: 칸 하나 고치기
print(a)

for i in range(1, 4):    # 구간 update: 1~3번 칸에 3씩 더한다
    a[i] += 3
print(a)

[4, 7, 12, 9, 5]
[4, 10, 15, 12, 5]

구간 작업은 구간 길이만큼 칸을 건드리므로 한 번에 O(n)이다. 질의가 m번이면 O(nm)이 되어, n과 m이 모두 10만이면 100억 번을 넘는다(2장). 문제는 대개 둘 중 한 모양으로 나온다.

칸 1~3의 합은 앞 4개(4, 7, 2, 9)에서 앞 1개(4)를 빼면 남는다. prefix[4] - prefix[1]은 22 − 4 = 18이고, 실제로 7 + 2 + 9도 18이다. 질문이 몇 번 오든 칸 두 개만 읽으면 된다. 약점은 값이 바뀔 때다. 칸 2를 고치면 그 칸을 품은 prefix[3], prefix[4], prefix[5]가 모두 틀려진다. 가계부에서 옛 거래 하나를 고치면 그 뒤 잔액을 전부 다시 써야 하는 것과 같다. 그래서 "배열은 그대로"라는 조건이 붙는다.

둘째, 차분 배열이 맞는 상황이다. 월요일부터 금요일까지 여는 숙소에 "화~목, 2명", "수~금, 1명" 같은 예약이 10만 건 들어온다. 화~목 2명은 화, 수, 목 사흘 모두 인원이 2씩 는다는 뜻이다. 예약 하나가 이어진 여러 날을 한꺼번에 바꾸므로 구간 update다. 예약을 다 받은 뒤 요일별 인원을 한 번 낸다.

예약마다 해당 요일을 하나씩 더하면 예약이 길수록 손이 많이 간다. 대신 들어오는 날에 +, 나가는 날(마지막 날의 다음 날)에 −만 적어 둔다.

마지막 줄은 표시를 월요일부터 차례로 더한 값이고, 이것이 요일별 인원이다. 예약을 하나씩 더해 봐도 월 0명, 화 2명, 수 3명, 목 3명, 금 1명으로 같다. 체크인에 +, 체크아웃에 −를 적어 두고 그날까지의 출입을 합치면 지금 묵는 사람 수가 되는 원리다. 예약이 아무리 길어도 칸 두 개만 고친다. 약점은 중간에 읽을 때다. 예약을 받는 도중 "목요일에 몇 명?"을 물으면 월요일부터 다시 더해야 한다. 그래서 "다 끝난 뒤 한 번 읽는다"는 조건이 붙는다.

셋째, 둘이 섞이는 상황이다. 누적합은 고치기가 느리고, 차분 배열은 읽기가 느리다. 고치기와 묻기가 번갈아 들어오면 어느 쪽을 골라도 질의의 절반이 O(n)이 된다. 이런 문제에는 다른 자료구조가 필요하며, 이 책에서는 다루지 않는다.

정리하면, 구간 질의는 배열을 한 번 다른 모양으로 바꿔 저장하면 빨라진다.

1차원 누적합

가계부의 잔액 칸을 떠올리면 쉽다. 잔액 두 개의 차이가 그 사이 기간의 지출이다. 누적합도 같다. prefix[i]를 앞 i개 원소의 합으로 정하고, 길이를 n+1로 잡아 prefix[0] = 0(앞 0개의 합)을 둔다.

그러면 구간 [l, r]의 합은 "앞 r+1개의 합"에서 "앞 l개의 합"을 뺀 값, 즉 prefix[r + 1] - prefix[l]이다.


def build_prefix(nums: list[int]) -> list[int]:
    prefix = [0] * (len(nums) + 1)     # 앞 0개의 합 자리를 하나 더 둔다
    for i, x in enumerate(nums):
        prefix[i + 1] = prefix[i] + x
    return prefix


def range_sum(prefix: list[int], l: int, r: int) -> int:
    return prefix[r + 1] - prefix[l]   # [l, r] 양 끝 포함


nums = [5, 2, 8, 1, 6, 3]
prefix = build_prefix(nums)
print(prefix)
print(range_sum(prefix, 1, 4), sum(nums[1:5]))
print(range_sum(prefix, 0, 5), sum(nums))    # l = 0 도 같은 식
print(range_sum(prefix, 3, 3), nums[3])      # 칸 하나짜리 구간

prefix[0]을 0으로 미리 두는 이유는 풀이가 편해서다. 이 0이 "앞 0개의 합" 자리라서, l이 0인 구간도 prefix[r + 1] - prefix[0]으로 같은 식 하나에 풀린다. 0 없이 길이 n으로 만들어도 되지만, 그러면 l이 0일 때를 따로 처리해야 한다. 7장의 accumulate(nums, initial=0)도 같은 배열을 만든다.

만드는 데 O(n), 질의마다 O(1)이다. 매번 sum()을 부르는 방법과 읽는 칸 수를 세어 비교하면 차이가 분명하다.


def naive_cost(queries: list[tuple[int, int]]) -> int:
    return sum(r - l + 1 for l, r in queries)    # sum() 이 읽는 칸 수


def prefix_cost(n: int, queries: list[tuple[int, int]]) -> int:
    return n + 2 * len(queries)                  # 만들기 n번 + 질의마다 두 칸


n = 100_000
queries = [(0, n - 1)] * 100_000     # 가장 나쁜 경우: 매번 전체 구간
print(f'{naive_cost(queries):,}')
print(f'{prefix_cost(n, queries):,}')

한 줄로 줄이면, 구간 합은 큰 앞부분에서 작은 앞부분을 빼서 구한다.

길이 k 구간의 최대 합

"연속한 k개의 합 중 가장 큰 값"은 누적합의 대표 응용이다. 시작 위치가 n-k+1가지이고, 각 구간의 합이 빼기 한 번이므로 전체 O(n)이다. 같은 문제를 21장의 고정 길이 창으로도 풀 수 있다. 창을 한 칸 밀 때 새로 들어온 값을 더하고 빠진 값을 뺀다.


def max_window_prefix(nums: list[int], k: int) -> int:
    prefix = [0] * (len(nums) + 1)
    for i, x in enumerate(nums):
        prefix[i + 1] = prefix[i] + x
    return max(prefix[i + k] - prefix[i] for i in range(len(nums) - k + 1))


def max_window_sliding(nums: list[int], k: int) -> int:
    window = sum(nums[:k])
    best = window
    for i in range(k, len(nums)):
        window += nums[i] - nums[i - k]    # 들어온 값 더하고 빠진 값 빼기
        best = max(best, window)
    return best


temps = [3, -1, 4, 6, -2, 5, 1, -3]
print(max_window_prefix(temps, 3), max_window_sliding(temps, 3))
print(max_window_prefix(temps, 5), max_window_sliding(temps, 5))

9 9
14 14

둘 다 O(n)이다. 차이는 쓰임새에 있다. 창은 메모리 O(1)로 한 방향으로 훑을 때 좋고, 누적합은 O(n)을 더 쓰는 대신 아무 구간이나 순서 없이 물어도 된다. 길이가 제각각인 질의가 섞여 들어오면 누적합이 맞다.

"합"만이 아니다

누적합이라는 이름에는 함정이 있다. 꼭 합일 필요도, 꼭 앞에서부터일 필요도 없다. 뒤에서부터 쌓으면 접미사 누적(suffix)이 되고, 더하기 대신 다른 연산을 쌓을 수도 있다. 예를 들어 "구간 안에 짝수가 몇 개인가"는 조건을 만족하면 1, 아니면 0을 쌓으면 된다. True가 1처럼 더해지기 때문이다(2장).


nums = [7, 4, 10, 3, 8, 6, 1]
even_prefix = [0]
for x in nums:
    even_prefix.append(even_prefix[-1] + (x % 2 == 0))
print(even_prefix)

l, r = 1, 4                                  # [4, 10, 3, 8]
print(even_prefix[r + 1] - even_prefix[l])

[0, 0, 1, 2, 2, 3, 4, 4]
3

codes = [5, 3, 6, 2, 7]

2차원 누적합

격자에서는 prefix[r][c]를 "왼쪽 위 모서리부터 r행 c열 직전까지의 직사각형 합"으로 정한다. 1차원처럼 0번 행과 0번 열을 0으로 비워 둔다. 만들 때는 위쪽 직사각형과 왼쪽 직사각형을 더하고, 두 번 더해진 왼쪽 위 겹침을 한 번 뺀 뒤 자기 칸을 더한다. 겹친 부분을 빼고 더해 맞추는 이 방식을 포함-배제라고 한다.


grid = [
    [3, 1, 4, 2],
    [2, 5, 1, 3],
    [6, 2, 3, 1],
]
rows, cols = len(grid), len(grid[0])
prefix = [[0] * (cols + 1) for _ in range(rows + 1)]
for r in range(rows):
    for c in range(cols):
        prefix[r + 1][c + 1] = (prefix[r][c + 1] + prefix[r + 1][c]
                                - prefix[r][c] + grid[r][c])


def rect_sum(r1: int, c1: int, r2: int, c2: int) -> int:
    return (prefix[r2 + 1][c2 + 1] - prefix[r1][c2 + 1]
            - prefix[r2 + 1][c1] + prefix[r1][c1])


for row in prefix:
    print(row)
print(rect_sum(1, 1, 2, 2))    # 5 1 / 2 3
print(rect_sum(0, 0, 2, 3))    # 격자 전체

[0, 0, 0, 0, 0]
[0, 3, 4, 8, 10]
[0, 5, 11, 16, 21]
[0, 11, 19, 27, 33]
11
33

격자가 R×C면 만드는 데 O(RC), 직사각형 질의는 칸 네 개만 읽으므로 O(1)이다. 행과 열이 하나씩 늘었을 뿐, 1차원과 생각은 같다.

차분 배열

이번에는 반대 상황이다. "[l, r]에 v를 더하라"가 수만 번 들어오고, 결과는 마지막에 한 번만 본다. 구간을 매번 다 고치는 대신, 시작점에 "여기서부터 +v"를, 끝 다음 칸에 "여기서부터 다시 −v"를 적어 둔다. 이렇게 이웃한 칸의 차이를 담은 배열을 차분 배열이라고 한다. 기록이 끝나면 누적합을 한 번 돌려 실제 값을 되살린다.


def apply_updates(n: int, updates: list[tuple[int, int, int]]) -> tuple[list[int], list[int]]:
    diff = [0] * (n + 1)          # r + 1 이 n 이 될 수 있어 한 칸 더
    for l, r, v in updates:
        diff[l] += v              # 여기서부터 v 만큼 올라간다
        diff[r + 1] -= v          # 여기서부터 원래대로
    result = []
    running = 0
    for i in range(n):            # 누적합으로 복원
        running += diff[i]
        result.append(running)
    return diff, result


updates = [(0, 2, 5), (2, 5, 1), (4, 4, 10)]
diff, result = apply_updates(6, updates)
print(diff)
print(result)

[5, 0, 1, -5, 10, -10, -1]
[5, 5, 6, 1, 11, 1]

수정 하나가 O(1)이고 복원은 O(n)이라, 수정 m개를 처리하는 데 O(n + m)이다. 이름이 왜 "차분"인지는 거꾸로 해 보면 보인다. 배열에서 이웃한 값의 차이를 뽑아 누적하면 원래 배열로 돌아온다.


from itertools import accumulate

nums = [4, 4, 7, 2, 2]
diff = [nums[0]] + [nums[i] - nums[i - 1] for i in range(1, len(nums))]
print(diff)                       # 이웃한 값의 차이
print(list(accumulate(diff)))     # 누적하면 제자리로

[4, 0, 3, -5, 0]
[4, 4, 7, 2, 2]

즉 차분과 누적합은 서로를 되돌리는 연산이다. 정리하면, 구간 더하기는 양 끝 두 점에 적고 마지막에 누적합으로 펼친다.

두 기술의 대칭

두 기술은 공짜가 아니다. 한쪽이 빨라지면 반대쪽이 느려진다. 누적합을 만든 뒤 원소 하나를 고치면, 그 뒤의 누적합이 모두 바뀐다. 원래 배열의 점 update가 누적합에서는 구간 update가 되는 것이다.


from itertools import accumulate

nums = [5, 2, 8, 1, 6, 3]
before = list(accumulate(nums, initial=0))
nums[2] += 4                                   # 점 update 한 번
after = list(accumulate(nums, initial=0))
print(before)
print(after)
print([i for i in range(len(before)) if before[i] != after[i]])

[0, 5, 7, 15, 16, 22, 25]
[0, 5, 7, 19, 20, 26, 29]
[3, 4, 5, 6]

차분 배열은 반대다. 값 하나를 읽으려면 diff[0]부터 그 칸까지 더해야 하니, 점 get이 구간 get이 된다. 그래서 수정 도중에는 읽지 않고, 모두 모은 뒤 한 번에 복원한다.

누적합차분 배열
빨라지는 것구간 get → 점 get 두 번구간 update → 점 update 두 번
느려지는 것점 update → 구간 update점 get → 구간 get
맞는 상황수정 없이 조회가 많다수정을 다 모은 뒤 조회한다
서로의 관계차분 배열을 누적하면 원래 배열, 원래 배열의 차분이 차분 배열이다

문제를 읽을 때 "무엇이 구간이고 무엇이 점인가, 수정과 조회가 섞이는가"를 먼저 따지면 둘 중 무엇을 쓸지 바로 정해진다.

자주 하는 실수

prefix 길이를 n으로 잡기

길이를 n으로 잡으면 마지막 원소가 어떤 누적합에도 들어가지 못하거나, l이 0일 때 prefix[-1]을 읽게 된다. 에러 없이 틀린 답이 나와 찾기 어렵다.


nums = [5, 2, 8]
prefix = [0] * len(nums)               # 한 칸 모자라다
for i in range(1, len(nums)):
    prefix[i] = prefix[i - 1] + nums[i - 1]
print(prefix)                          # 마지막 원소 8 이 어디에도 없다
print(prefix[2] - prefix[0])           # 전체 합 15 를 기대했다

[0, 5, 7]
7

길이를 len(nums) + 1로 잡고 prefix[r + 1] - prefix[l]을 쓰면 해결된다. 차분 배열도 diff[r + 1]에 쓰므로 한 칸 여유가 필요하다.

2차원에서 겹친 부분을 되돌리지 않기

위쪽과 왼쪽을 빼고 끝내면 왼쪽 위 모서리 영역이 두 번 빠진다. 직사각형 합에서는 + prefix[r1][c1]을, 만들 때는 - prefix[r][c]를 빠뜨리지 않았는지 확인한다.

질의마다 sum(a[l:r+1])

코드는 짧지만 슬라이스가 구간을 복사하고(3장) sum이 다시 훑어서 질의 하나가 O(n)이다. 예제는 통과하고 큰 입력에서 시간 초과가 난다.

차분 배열을 복원하지 않고 읽기

diff[i]는 i번 칸의 값이 아니라 "i번에서 값이 얼마나 바뀌는가"다. 결과를 내기 전에 반드시 누적합으로 펼친다.

대표 문제

Problem쉬움누적합

구간 합 질의

어느 전시관의 N일 동안 일별 방문자 수가 주어진다. 질의 M개가 들어오는데, 질의 l r은 l일부터 r일까지(양 끝 포함) 방문자 수의 합을 묻는다. 각 질의의 답을 한 줄에 하나씩 출력하라.

첫 줄에 N과 M(1 ≤ N, M ≤ 100,000), 둘째 줄에 방문자 수 N개(각각 0 이상 1,000 이하)가 주어진다. 다음 M줄에 l과 r(1 ≤ l ≤ r ≤ N)이 주어진다. 날짜는 1일부터 센다.

접근 방법먼저 생각해 보고 펼치세요

매번 더하면 최악에 100억 번이다. 배열이 바뀌지 않고 구간 get만 많으니 누적합을 한 번 만들어 두고 질의마다 빼기 한 번으로 답한다.

  1. 길이 N+1의 prefix를 만든다. prefix[i]는 1일부터 i일까지의 합이다.
  2. 날짜가 1부터 시작하므로 l~r일의 합은 prefix[r] - prefix[l - 1]이다. 0번 칸 덕분에 l이 1이어도 같은 식이 통한다.
  3. 답을 리스트에 모아 마지막에 한 번에 출력한다(1장).
풀이 코드 

import sys

input = sys.stdin.readline

n, m = map(int, input().split())
visitors = list(map(int, input().split()))

prefix = [0] * (n + 1)              # prefix[i] = 1일부터 i일까지의 합
for i in range(n):
    prefix[i + 1] = prefix[i] + visitors[i]

answers = []
for _ in range(m):
    l, r = map(int, input().split())
    answers.append(prefix[r] - prefix[l - 1])
print('\n'.join(map(str, answers)))

스스로 확인

누적합 배열의 길이를 n이 아니라 n+1로 잡는 이유는?

prefix[0] = 0을 "앞 0개의 합"으로 두기 위해서다. 그러면 l이 0인 구간도 prefix[r + 1] - prefix[l] 하나로 풀리고, 마지막 원소까지 포함한 합 prefix[n]도 들어갈 자리가 생긴다.

XOR 누적으로는 아무 구간이나 되는데, 누적 최댓값으로는 왜 안 되는가?

구간 값을 얻으려면 앞부분을 지워야 하고, 그러려면 역연산이 필요하다. XOR는 같은 값을 다시 XOR하면 지워지지만, max는 한 번 큰 값에 덮이면 그 앞의 정보를 되살릴 수 없다. 누적 최댓값은 맨 앞부터의 구간에만 답한다.

2차원 직사각형 합 공식에서 prefix[r1][c1]을 마지막에 더하는 이유는?

위쪽 직사각형 prefix[r1][c2 + 1]과 왼쪽 직사각형 prefix[r2 + 1][c1]에 왼쪽 위 영역이 모두 들어 있어서 두 번 빠진다. 한 번만 빠져야 하므로 한 번 되돌려 더한다.

"구간에 v 더하기"와 "한 칸 값 읽기"가 번갈아 수만 번 들어온다. 누적합과 차분 배열이 모두 느린 이유는?

누적합을 쓰면 구간 더하기가 뒤쪽 누적합 전체를 고치는 일이 되어 O(n)이다. 차분 배열을 쓰면 더하기는 O(1)이지만 한 칸을 읽을 때마다 앞부터 더해야 해서 O(n)이다. 둘 다 한쪽이 O(n)으로 남는다. 이런 경우는 펜윅 트리나 세그먼트 트리처럼 양쪽을 모두 O(log n)에 하는 자료구조가 필요하다.

정리

  1. 구간 질의 문제는 먼저 점/구간, get/update를 가르고, 수정과 조회가 섞이는지 본다.
  2. 누적합은 길이 n+1로 만들고, 구간 [l, r]의 합은 prefix[r + 1] - prefix[l]이다. 만들기 O(n), 질의 O(1)이다.
  3. 길이 k 구간의 최대 합은 누적합과 21장의 고정 창 모두 O(n)에 풀린다.
  4. 합 말고도 개수, XOR처럼 역연산이 있는 연산은 누적할 수 있다. max, min, gcd는 앞부분 구간에만 쓴다.
  5. 2차원 누적합은 포함-배제로 만들고, 직사각형 합은 칸 네 개로 구한다.
  6. 차분 배열은 구간 더하기를 diff[l] += v, diff[r + 1] -= v로 적고, 마지막에 누적합으로 복원한다.
  7. 두 기술은 서로 대칭이다. 한쪽 작업을 빠르게 하는 대신 반대쪽 작업이 느려진다.
